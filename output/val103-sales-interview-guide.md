# VAL103 售前访谈提纲

更新日期：2026-04-17

## 访谈目的

用于和客户公司的售前、方案经理或资深应用工程师确认：

1. 人工筛选“相似历史方案”时真实使用的判断维度
2. 哪些维度是硬门槛，哪些只是加分项
3. 哪些关键词经常造成误判
4. 他们更看重“整份方案相似”还是“某一章节可复用”

这份访谈的目标不是讨论模型，而是沉淀后续 `evidence bundle` 检索和 `VAL103` 判定的业务规则。

## 访谈对象建议

- 售前负责人
- 主方案工程师
- 熟悉历史方案库的资料管理员
- 参与过中标/投标复盘的人

建议至少访谈 2 类角色：

- 一个偏业务侧
- 一个偏技术侧

## 访谈前准备

访谈前建议准备：

1. 2 到 3 份“判断为很像”的历史方案
2. 2 到 3 份“看起来像但实际上不能复用”的方案
3. 当前目标需求摘要
4. 一张空白的《相似方案判断表》

## 核心访谈问题

### 一、人工筛选流程

1. 你们人工找历史相似方案时，第一步先看什么？
2. 你们通常是先缩小到某类项目，再看具体技术方案，还是直接全文检索？
3. 你们更习惯先找“整份最像的方案”，还是先找“某一章最像的材料”？
4. 一份方案从“看一眼”到“确定可复用”，通常会经过哪几步？

### 二、硬约束维度

1. 哪些条件不匹配，就基本不会继续看？
2. 行业是否必须一致？
3. 工艺对象是否必须一致？
4. 电压等级是否必须一致？
5. 设备对象是否必须一致？
6. 启动方式是否必须一致？
7. 控制架构或接口方式是否有必须一致的部分？

### 三、强加分维度

1. 除了硬约束，哪些信息会明显提高你们对“相似”的判断？
2. 你们会不会优先看供货范围、主回路、控制联锁、技术参数这些特定章节？
3. 如果项目参数不完全一致，但章节结构和技术路线很像，你们会认为它是高价值参考吗？
4. 图纸、表格、接口点表对你们判断相似性有多重要？

### 四、噪声与误判

1. 哪些词经常让方案“看起来相关”，但实际上没价值？
2. 哪些项目容易被误判为相似？
3. 哪些标题、术语或行业词会造成误召回？
4. 对你们来说，哪些章节通常不值得复用？

### 五、章节级复用

1. 如果整份方案不够像，但某几章很像，你们会接受吗？
2. 哪些章节最适合跨项目复用？
3. 哪些章节必须按当前项目重写，不能简单复用？
4. 你们判断一章“可复用”的标准是什么？

### 六、结果呈现与信任

1. 系统如果给你们推荐 3 份相似方案，你们最希望看到哪些解释信息？
2. 你们更想看到“为什么像”，还是“为什么不该复用”？
3. 如果系统说“相关性高”，你们希望这个判断建立在哪些依据上？
4. 什么样的推荐结果会让你们愿意相信系统，而不是自己重新找？

## 建议追问

如果对方回答比较抽象，建议追问：

- “请用最近一个真实项目举例”
- “这个条件是必须一致，还是最好一致？”
- “如果只能保留 5 个判断维度，你会留哪 5 个？”
- “这个因素在整份方案层面重要，还是在章节层面重要？”

## 访谈产出

访谈结束后，至少应形成以下产出：

1. 一份排序后的“相似方案硬约束/强加分/弱加分/排除项”列表
2. 一份“高价值复用章节”清单
3. 一份“高噪声关键词/误判模式”清单
4. 一份可直接映射到检索逻辑的维度权重表

## 推荐沉淀格式

建议最终按下面四类沉淀：

- 硬约束
- 高权重加分项
- 低权重加分项
- 明确排除项

并按两个层面分别记录：

- 整份方案层
- 章节材料层

## 对应系统改造映射

访谈结论可直接映射到后续代码优化：

- `build_requirement_query(...)`
  适合接入：高权重关键词、关键参数、工艺对象、设备对象

- `retrieve_evidence()`
  适合接入：整份方案级筛选条件、fallback 策略

- `quality_score`
  适合接入：硬约束命中、章节价值、fallback 有效性

- `VAL103`
  适合接入：是否真正缺证据，还是只是缺精确 chunk 证据
