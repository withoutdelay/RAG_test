# Reuse-First 检索重构 PRD

更新时间：2026-04-02

## 1. 产品目标

把当前 `reuse-first` 从“chunk 主导的复用生成”重构为“章节主导的复用生成”，显著提升短查询场景下的命中准确度、章节信息密度和生成可控性。

本轮目标不是做新 UI 包装，而是先把生成质量最核心的上游链路做对。

---

## 2. 需要解决的问题

当前主问题：

1. 文档切分过碎，章节语义被拆散
2. 短查询容易命中词面相近但章节不对的 chunk
3. 组装给模型的上下文来自多个碎片，导致章节成稿质量不稳
4. 章节标题与正文材料的对应关系不够强，复用痕迹难追踪

---

## 3. 目标用户

- 售前工程师
- 方案经理
- 需要快速复用历史方案章节的交付团队

他们的核心诉求不是“生成一篇看起来像样的稿子”，而是“尽可能命中最像的历史章节，并少改几刀就能交付”。

---

## 4. 核心需求

### 4.1 章节作为第一检索单元

- 系统必须先判断“目标章节最像历史库中的哪几个章节”
- 章节标题、标题别名、标题家族、目录邻接关系必须成为主排序信号
- 用户补充的章节 purpose / 细节描述应作为第二排序信号

### 4.2 chunk 降级为章节内部证据

- chunk 仍保留，用于：
  - 章节内部正文选择
  - 表格/图资产挂接
  - 精细引用
- 但 chunk 不能再独立主导章节候选排序

### 4.3 支持两种生成输入模式

#### A. Section-Pack Mode

默认模式，向模型提供：

- 目标章节信息
- Top 章节候选摘要
- 各候选章内精选正文块
- 关联表格/图/公式资产

#### B. Full-Section Mode

当满足以下条件时允许触发：

- 章节命中足够强
- 候选章 token 在预算内
- 同名章节冲突较小

此时向模型提供 1 到 2 个完整源章节正文，并补充必要的资产与替换约束。

### 4.4 强制可追溯

每个 `reuse_first` 章节都必须能追溯：

- 命中的历史章节
- 进入 prompt 的正文块
- 进入 prompt 的资产
- 排序理由

### 4.5 失败时稳健回退

以下情况必须回退：

- 没有高置信章节候选
- token 超预算
- 候选章节标题过于泛化
- 强命中章节被识别为高风险或高噪声

回退策略：

- 从 `full-section mode` 回退到 `section-pack mode`
- 再必要时回退到当前 `baseline`

---

## 5. 非目标

本轮不做：

1. 大规模前端视觉重做
2. 新增全新对外 API
3. 依赖 prompt 微调解决检索根因
4. 一次性重做所有 ingestion / OCR / asset pipeline

---

## 6. 成功标准

本轮至少要建立以下评估指标：

1. `section_retrieval_top1`
   - 目标章节的正确历史章节是否排在第 1
2. `section_retrieval_top3`
   - 正确历史章节是否进入前 3
3. `generated_section_density`
   - 成稿的信息密度不能明显低于主源章节
4. `source_trace_coverage`
   - 所有 `reuse_first` 章节都能看到来源章节与来源块
5. `manual_edit_reduction`
   - 人工修改量相对当前链路显著下降

---

## 7. 范围边界

本轮产品范围聚焦后端链路：

- 文档结构真值
- 章节级检索
- 章节内块选择
- 生成输入装配
- 调试与可追溯输出

前端只需要为后续实现预留可观测界面，不要求本轮先做视觉交付。

---

## 8. 本轮决策

本轮 PRD 结论：

1. 同意把“章节”提升为主检索单位
2. 不采用“只按章节名检索整章并直接全喂模型”的纯单层方案
3. 正式采用“章节优先、块级补充、条件式长上下文”的层级方案
4. 后续实现按此 PRD 驱动架构改造与评估集建设
